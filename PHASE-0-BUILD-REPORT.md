### The bug this fixes

v1.4.0's queue could only move forward:

```js
c.step = Math.min((c.step||0)+1, 4);   // step never decreases
```

A card you blanked on completely still advanced to a longer interval. There was one
button — "Recalled ✓" — so the system had no way to even *hear* that you'd failed.
Every fumbled card was being mis-scheduled, and the more you struggled with an item
the further out it drifted.

v1.5.0 grades each review and gives **Again** a real lapse path:

| Grade | On a card last seen 10 days ago (S=20) | Lapse recorded |
|---|---|---|
| Again | stability 20 → 1.4, back in **1 day** | ✅ |
| Hard | back in 34 days | — |
| Good | back in 43 days | — |
| Easy | back in 63 days | — |

### New card shape

```js
{ q, a?, key?, stability, difficulty, due, state, reps, lapses, last_review }
```

`step` is retired. A new card starts `stability: null` — FSRS derives the first
stability and difficulty from *how the first review actually went*, rather than
assuming a starting point.

### Migration

Non-destructive and idempotent. Old `step` becomes the initial stability estimate
via the retired ladder, difficulty starts neutral at 5.0 and converges after a
review or two:

| old `step` | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| new `stability` (days) | 1 | 3 | 7 | 16 | 35 |

Existing `due` dates are preserved exactly; a card with no `due` gets one. Nothing
else in the profile is touched.

### Auto-enqueue

Mastering a glossary term in a lesson quiz now files a review card automatically —
front `"What does X mean?"`, back the definition, keyed `term:<slug>`. Re-mastering
the same term does **not** create a second card. The `+ Add card` button routes
through the same `enqueueCard()` path and now asks for an optional back.

### The oracle test is the important one

The risk with inlining is silent drift — a mistyped exponent produces a scheduler
that looks fine and quietly schedules everything wrong. So the FSRS block is
**sliced straight out of `index.html`** by `extract.sh` (never retyped) and run
against `fsrs6-oracle.json`, which was generated by **py-fsrs 6.3.2** — not by ARC
and not by AEGIS. It covers every function plus five full multi-review sequences
driven end-to-end through `fsrsNew`/`fsrsReview`, including banker's rounding
(D14) — the half-up/half-to-even distinction that costs a full day at every exact
`.5` boundary.

### Every suite is fault-injection tested

A green suite means nothing until you've watched it go red. Each defect below was
reintroduced into a copy and the suite re-run:

| Injected defect | Caught by |
|---|---|
| Half-up rounding instead of banker's | 5 oracle failures |
| Again routed through the recall formula | 3 oracle + 3 app failures |
| `lapses` never incremented | 3 app failures |
| Migration disabled | 8 app failures |
| Dedupe removed from `enqueueCard` | 2 app failures |
| Reveal broken | 1 app failure |
| Version bump missed in the header | 1 app failure + lockstep FAIL |
| Template copy left on the old ladder | 1 app failure |

The lapse-path injection initially passed the app suite. The seeded cards all had
`last_review = now`, so grading them took the **same-day** branch and never reached
the lapse formula at all. Fixed by adding a card last reviewed 10 days ago — the app
suite now catches it in three places. Worth recording: the test looked thorough and
was blind to the exact defect the release exists to fix.
